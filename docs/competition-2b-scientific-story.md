# 挑战杯 2B「日冕加热之谜」科学故事与产出规范

## 1. 项目定位

本项目不是把某个日冕加热理论作为输入让大模型寻找支持，而是从观测现象出发，生成并比较可能的物理解释，把一个非唯一的太阳物理现象转化为可检验、可追溯、可停止的科学验证流程。

一句话摘要：

> 面向日冕多波段热响应和间歇性增亮现象，系统从现象特征和相关文献中生成竞争机制解释，将每个解释拆成原子预测和证伪条件，由确定性科学执行器完成测量，由独立性、能力和证据门禁比较解释与观测的匹配程度，并在证据不足时给出下一项有明确成功判据的验证任务。

## 2. 结构化输入

一次运行的入口是 `PhenomenonInput`，而不是自由文本对话：

| 字段                    | 含义                                                   |
| ----------------------- | ------------------------------------------------------ |
| `phenomenonId`          | 现象的稳定 ID                                          |
| `title` / `description` | 现象标题和可读描述                                     |
| `activeRegion`          | 目标活动区（可选）                                     |
| `observations`          | AIA/HMI/IRIS/EIS/NuSTAR 等观测引用、波段、时间、校验和 |
| `requestedQuestion`     | 要区分的科学问题                                       |
| `constraints`           | 时间窗、数据、仪器或分析限制                           |

理论不是用户预先给出的答案，而是候选解释空间的来源。系统先读取现象的时间、空间、波段和活动区特征，再从核验文献和已登记机制中提出候选；理论只提供“如果该机制成立，应该看到什么”和“什么结果会削弱它”的约束。

本题的示例问题是：

> AR11158 及独立活动区中出现的多波段热增强和有序冷却，能否通过可重复的观测预测区分脉冲加热、磁重联/纳耀斑、阿尔芬波耗散及替代热过程？

## 3. 科学处理链

```text
现象特征与观测引用
  -> 相关理论检索和竞争解释生成
  -> 原子预测 / 证伪条件
  -> 预测与执行器能力匹配
  -> AIA/HMI/IRIS/EIS/NuSTAR 确定性处理
  -> 证据、反例、独立事件和数据谱系审计
  -> 逐假设门禁判定
  -> 增量验证任务或有边界停止
```

大模型只负责从现象寻找相关理论、提出解释、解释结果和规划；数据测量、来源校验、区间计算、独立性审计和最终状态由代码完成。系统输出的是“当前观测更符合哪些解释、哪些解释仍不可区分”，不是未经验证的机制概率。

## 4. 对外展示的候选机制

内部可以保留完整候选池，P5 对外只展示 3--4 个机制族：

| 假设             | 可检验预测                                   | 当前边界                                 |
| ---------------- | -------------------------------------------- | ---------------------------------------- |
| 脉冲加热过程     | 热通道间歇峰、跨通道冷却、DEM 温度演化       | 可支持受限热过程，不等于纳耀斑已证实     |
| 磁重联/纳耀斑    | 热峰与磁能释放、高温或 HXR 信号、跨事件复现  | 仍缺完整 HXR 物理提取、磁拓扑和能量预算  |
| 阿尔芬波传播耗散 | 环结构传播、相速度、频率依赖阻尼、波能流闭合 | 当前只有空间波动代理，不能宣称波加热成立 |
| 替代或耦合过程   | 长时段热非平衡，或波动/重联联合预测增益      | 需要长时段对照或匹配 MHD 前向模型        |

## 5. 结构化输出

一次科学运行至少输出以下对象：

1. `hypotheses`：从当前现象生成的候选解释、机制组成、预测、证伪条件和来源。
2. `evidence`：观测到的事实、方法、来源、样本、预测绑定、点估计、区间、限制和 provenance。
3. `verificationReports`：每条假设的支持/反例数量、独立事件、观测量族、方法族、预测覆盖、holdout 和门禁原因。
4. `validationTasks`：下一步任务、所需数据/设施、执行器、就绪度、周期、成功判据、失败判据和结果证据 ID。
5. `scientificStatus`、`closureStatus`、`workflowClosure`、`operationalClosure`：分别表达解释是否得到充分证据、证据闭环、工作流完整性和运行完整性。

对外可以把这些对象阅读成三个结果：

```text
现象画像：实际观测到的变化和数据质量
解释比较：每个候选机制与观测预测的匹配、反例和未知项
行动建议：下一项最能减少未知的观测、分析或模拟任务
```

“闭环完成”表示每条假设都有终局处置、每个证据可追溯、每个缺口都有计划；它不表示所有机制都已被证明。

## 6. 多智能体问题审计与修复

此前的主要问题不是“智能体数量不够”，而是阶段职责和产出没有形成可验证契约：部分 agent 在后续轮次重复读取同一数据，已完成任务会再次触发处理；C 阶段的裁决只改变假设状态，却没有在 agent 执行账本中留下裁决者和输入输出；D 阶段可以提出当前轮数无法执行的本地任务，导致 `maxRounds` 看起来像装饰参数；人审、外部数据和本地执行器缺口也没有被区分。现在的修复如下：

| 阶段 | 科学智能体职责               | 原问题                                                                         | 当前修复与可审计产出                                                                                                                                                |
| ---- | ---------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A    | 文献溯源与候选机制生成       | 只记录假设内容，无法证明候选由哪个 agent、哪一轮生成                           | `librarian` 记录 stage/round/capabilities，并绑定 `outputHypothesisIds`；保留假设谱系和来源，不输出未经验证的概率                                                   |
| B    | 观测质控、物理诊断、反证审计 | 已完成任务被当作新任务重复处理；同一处理产物在不同轮次产生重复证据             | 只消费 `planned` 且有注册执行器的任务；处理缓存键改为输入数据、模式和处理版本，不含 round；证据按稳定 ID 去重，只流式发送新增证据                                   |
| C    | 证据门禁、交叉验证和结论裁决 | 支持性条数被误读为支持假设；过强结论没有独立审计记录                           | `sisyphus` 记录裁决输入输出，执行严格独立事件、观测量族、方法族、holdout、功效和区间门禁；不满足时降为 `unknown`/`provisionally_supported`/`deferred_requires_data` |
| D    | 验证设计、任务路由和预算审计 | 只返回下一步文本，无法判断任务是否可执行；最终轮仍登记伪 `executable_now` 任务 | `prometheus` 记录任务 ID；逐项检查 executor/readiness；最终轮省略无法执行的本地任务并累计 `roundBudget.deferredTaskCount`；路由只在有新信息和可执行任务时继续       |

每条执行记录现在包含 `agentId`、`stage`、`round`、`status`、`capabilities`、`outputHypothesisIds`、`outputEvidenceIds` 和 `outputTaskIds`。最新 Docker + Helix 运行共有 15 条执行记录，覆盖 A/B/C/D 四阶段；`operationalClosure` 会据此检查失败 agent、失败任务、未解决 error correction 和数据完整性，而不是依据 UI 文案猜测“运行成功”。

这套修复还明确区分三种“结束”：`workflowClosure=complete` 只表示每条假设和任务有终局处置；`operationalClosure=complete` 表示 agent/执行器/数据完整性没有失败；`closureStatus=partial` 或 `scientificStatus=needs_data` 仍表示科学问题没有被证明。这样“工程闭环完成”不会再被错误宣传为“日冕加热机制已解决”。

## 7. 当前真实结果

当前冻结基线为 Docker + Helix 实跑 `run-1788431926970-1f3b6181`（2026-09-03）：

- 15 条假设、144 条证据、29 项验证任务，其中 18 项已完成，11 项因需要外部数据或设施保留为 `planned`；
- 失败任务、失败智能体和未解决 error correction 均为 0；
- 1 条假设仅达到受限过程层 `provisionally_supported`，其余 14 条为 `deferred_requires_data`，没有具体加热机制通过严格支持门槛；
- `scientificStatus=needs_data`、`closureStatus=partial`；
- `workflowClosure=complete`、`operationalClosure=complete`。
- 终止原因为 `no_executable_validation_task`：剩余任务都需要当前环境之外的数据或执行器，而不是因为必须机械跑满轮数。

正确的比赛表述是：

> 系统从现象出发生成并比较多个物理解释，完成了证据链、反例审计和验证计划的科学闭环；现有数据支持部分受限热过程预测，但尚不足以区分具体日冕加热机制，因此系统明确输出 `needs_data`，没有把流程完成改写成机制结论。

## 8. 下一步验证计划

下一步不再写成“继续跑一轮”，而按预测缺口登记任务：

| 目标          | 验证任务                                                   | 成功判据                                                     |
| ------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| 磁重联/纳耀斑 | 独立事件的热峰、磁拓扑、能量释放和 NuSTAR 源/背景/响应分析 | 全部预注册预测在 holdout 上复现，且有完整 95% 区间和能量预算 |
| 阿尔芬波      | 人工核验环路径，测密度、相速度、振幅、阻尼和能流           | 频率依赖阻尼及波能流能解释观测损失                           |
| 替代热过程    | 更长 AIA 窗口、DEM、冷却时延和同区背景对照                 | 在独立事件上区分脉冲与近稳态解释                             |
| 波动-重联耦合 | 观测匹配 MHD 前向模型、响应卷积和组件消融                  | 耦合模型在留出事件上相对单机制模型有预注册增益               |

每个任务只有在存在新的数据谱系、观测量族、方法、holdout 或模型版本时才进入下一轮；否则直接以 `no_new_information` 或 `no_executable_validation_task` 停止。

`maxRounds` 是计算预算上限，不是科学闭环的必需次数。提交 Demo 使用 `maxRounds=2` 足以展示“提出—测量—复核—规划”两轮；如果在预算内已经没有可执行任务，后端优先报告 `no_executable_validation_task`，保留待外部验证的任务，不为追求轮数而重复处理同一数据。

## 9. 多轮执行约束

多轮是“新增科学信息后的再审计”，不是固定批处理次数：

- A 阶段只在现象改变或模型更新任务触发时重做；
- B 阶段只消费 `planned` 且有本地执行器的任务；
- 已完成任务保留用于 provenance，但不得再次触发处理或模型审阅；
- 相同输入、处理版本和原始指纹必须复用同一产物 ID；
- 下一轮必须报告新增证据、改变的门禁状态和新增任务，否则停止。

这套规则保证“下一步方案”真正改变验证空间，而不是增加同一 WCS、重投影或热通道记录的副本。

## 10. 提交边界

不应声称：已经解决日冕加热、已经实现完整 MHD 模拟、或辅助机器学习输出了机制概率。应提交：真实输入、确定性证据、反例和限制、机器可读结果、一键复现命令、数据/模型许可证和成功与局限案例。
